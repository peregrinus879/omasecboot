## T-6.2 Decision Record

- Producer lease admission and obligation derivation are pinned to `limine-mkinitcpio-hook` 1.38.0-1 and `limine-snapper-sync` 1.31.0-1. `limine-mkinitcpio-hook` owns `/usr/bin/limine-mkinitcpio`. UKI inventory and every repository hook derive package obligations from `/usr/lib/modules/*/modules.builtin`; `pkgbase` is not an authority.
- Only the package PreTransaction guard consumes `NeedsTargets`. Cleanup and final repair identify the validated live coordinator from the durable producer record and use its immutable pre-recorded target set rather than recomputing authority from post-hook input.
- Producer suppression and completion use the external coordinator's immutable record, exact identity, boot ID, process start time, and current ancestry. Top-level OmaSecBoot descendants use the separate transaction-token protocol.
- A separate Remove-only PreTransaction guard preserves the exact recovery command providers, pinned producer runtime dependencies, active watcher support, and supported configured hash utilities while lifecycle state is managed. The protected set includes `tar`, `libnotify`, `inotify-tools`, `b3sum`, and `xxhash` alongside the core repair stack. The hook consumes no target stream, runs before producer admission, and evaluates removal under both boot locks. Generic lifecycle mutation checks the canonical pacman database lock after acquiring those locks and immediately before publication, closing concurrent adoption after the removal hook returns. OmaSecBoot package removal runs through pacman under this guard and removes only package content.
- Package target capture is bounded to 16,384 lines and 491,520 raw bytes so JSON escaping cannot exceed the 1 MiB control-document boundary; malformed or over-limit input is fully drained and blocks admission. Tests pin exact acceptance and one-line-over rejection at both limits. Rechecked 2026-09-04: the conservative installed inventory from every `linux-firmware*` package remains 6,620 `/usr/lib/firmware` paths and 363,115 bytes including leading slashes, within both activation bounds. Re-measure the actual ALPM target stream before widening producer targets or lowering either bound.
- Active lifecycle blocks direct package changes to the five pinned producer and recovery packages, including `sbctl`, because a PreTransaction query can prove only the installed version, not the incoming archive version. Disabled or pristine state remains the upgrade path; package dependency pins provide the normal release boundary. Even an initially inactive package guard acquires both boot locks and re-reads lifecycle state before returning; the pacman database lock then prevents activation from publishing against a package transaction that was already admitted.
- `producer_reconstruction_preflight()` is the only relaxed preflight and tolerates missing expected producer outputs only before fixed-registry reconstruction. Canonical artifact repair retains the strict `artifact_repair_preflight()` boundary.
- Producer lease publication requires stable `active` state. `unmanaged` and `disabled` package and Limine hooks remain no-state-write paths; `transition` and `recovery-required` fail closed unless validated producer recovery owns the transition. Public adoption requires known originals, operation-selected lifecycle repair, the exact supported recovery toolchain, and the current installed hook set, so it cannot strand a user in `active` state without unconfiguration or producer interception.
- A proved snapshot-watcher descendant uses `service_policy: preserve-owner`; other producer contexts use `quiesce`. Full restore uses its exact process identity and an inode-bound upstream marker for specialized admission, while generic package admission remains marker-blocked and normal post-repair preserves the upstream-owned marker. Stale restore recovery scans for the exact root wrapper, sync script, and native worker, removes the marker pathname only while it still matches the recorded inode after durable incident publication under both locks, and leaves snapshot reconstruction marker-blocked against a new admission race. Same-boot stale transition reconciliation requires the recorded marker; cross-boot reconciliation and an existing validated recovery incident may accept absence after another clear process scan.
- An inherited FD 200 handoff reacquires the validated inherited open file description after reconstruction. If that reacquisition fails, recovery attempts the current canonical pathname's validated lock. Failure to acquire either lock leaves the durable transition unchanged for later reconciliation under both locks; the Limine post-hook returns a fatal status, so the calling mutation terminates without relying on the parent's unlocked descriptor.
- Managed-settings ownership is written before tracking ownership, so a failed producer repair may expose no pair or a managed-only frontier; tracking-only is invalid. A later recovery selects the newest complete pair in the validated incident chain and falls back to stable lifecycle ownership only when no incident transaction has complete authority. Idempotent failed and resolved recovery publication re-syncs the lifecycle file and its parent before releasing transaction context after a prior post-rename uncertainty.

## T-6.3 Decision Record

- Rechecked 2026-09-02: Arch ships `sbctl` 0.18-2 and upstream 0.18 remains the latest release. The tagged `enroll-keys` source permits `--partial` only for `db`, `KEK`, and `PK`; export writes those same three hierarchies, and no dbx writer exists. Firmware continuation remains pinned to `/usr/bin/sbctl` from that package and the exact confirmed `-m -f` plan.
- Incident recovery has an exhaustive operation map. A root with immutable producer evidence admits only `producer-recovery`; an `enroll-secure-boot` root without producer evidence admits only `firmware-recovery`. Other root operations cannot acquire a recovery attempt through these component gates.
- Firmware recovery takes no caller backup identifier. It traverses only validated, hash-bound prior lifecycle records from the failed root to the exact completed `activate-secure-boot-plan` transaction and derives the firmware-backup and confirmed-plan binding from that manifest. Successful unconfiguration terminates this setup lineage. A root that failed before binding may acquire only that derived binding in its recovery attempt; later attempts inherit it exactly.
- Every attempt inherits the immediate predecessor's firmware ledger. A terminal pending record is classified against direct F0-F3 observation as `unchanged`, `verified`, or a coherent failure before any retry; technical readback uncertainty leaves it pending. A known state outside the permitted pre-write or post-write frontier is `failed`, terminal to automatic recovery, and retained for a future explicit recovery procedure. The existing six-record and two-per-hierarchy limits apply to the complete incident chain rather than restarting per attempt.
- Recovery keeps file restoration available only while the inherited ledger is empty and direct state remains F0. Otherwise it preserves the proved boot-artifact set. Every continuation repairs and proves EFI artifacts before a remaining firmware write and completes only after F3, a second EFI verification, and transaction-local firmware and schema-2 artifact proofs. T-6.3 made only the internal recovery capability available; T-6.8 activates firmware enrollment, the dispatcher, and consolidated repair together.

## T-6.4 Decision Record

- Rechecked 2026-09-03: Arch ships `efibootmgr` 18-4 and upstream release 18 remains latest. The guarded writer is pinned to that package and `/usr/bin/efibootmgr`; the package hooks block its replacement during a managed lifecycle, package ownership is proved directly, and one validated open inode supplies the executable hash, final target query, and write. Revalidate package, release, option parsing, write width, and executable ownership before accepting another version.
- Linux efivarfs exposes four little-endian attribute bytes followed by payload. BootNext is accepted only as a root-owned, non-writable-by-group-or-others, six-byte regular file with attributes `NV|BS|RT` (`7`) and one little-endian UINT16. Absence is recorded distinctly. Any mount, metadata, size, attribute, identity, or read uncertainty blocks before mutation or leaves a published transaction recoverable.
- A root `windows-bootnext` transaction publishes a create-once schema-1 record containing the boot ID, exact persisted target, prior BootNext state, and pinned tool evidence before its only write. It then repeats the boot-ID, prior-value, executable-hash, and full target proof immediately before `efibootmgr -n`, and requires exact direct efivarfs readback plus another complete target proof. Command success alone never commits. Every post-publication failure remains `recovery-required` for T-6.5 resolution.
- T-6.4 left the mutation predicate and public dispatcher closed while hermetic tests exercised the internal boundary, command failure before and after effect, prior/target/tool races, malformed efivar data, mismatched readback, and interruption after write without claiming any real firmware mutation. T-6.8 activates that tested route through operation-selected recovery.
- The shared locks and package hooks serialize OmaSecBoot, Limine, package, and known producer activity, not arbitrary root processes or autonomous firmware changes. Immediate pre-write checks and a final BootNext read after the second target proof narrow that residual race but cannot exclude a non-cooperating external writer after the final observation.

## T-6.5 Decision Record

- Rechecked 2026-09-03: Arch still ships `efibootmgr` 18-4 and coreutils 9.11-2. efibootmgr 18's `-N` branch checks `is_current_entry(opts.delete_bootnext)`, where the option is a boolean set to one, so BootNext deletion incorrectly requires `Boot0001`. Recorded absence is restored by the one-path GNU `unlink` interface instead. The package hooks treat coreutils as a pinned producer; recovery proves package ownership, hashes and opens `/usr/bin/unlink`, records that tool plus the BootNext pathname, device, inode, and hash before mutation, re-proves those fields immediately before pathname-based unlink, executes the open tool inode, and requires direct absence readback. Recheck both package versions, the `-N` implementation, coreutils invocation, and efivarfs deletion behavior before accepting another version or changing this boundary. Because active lifecycle blocks a coreutils package transaction, revalidate and update the pin, package dependency, hooks, and tests while lifecycle is disabled or pristine before supporting a new coreutils release.
- A `windows-bootnext` root without a published BootNext record admits only `windows-recovery` and resolves as `not-published` without reading or writing efivarfs. With a record, immutable completed-phase evidence classifies whether the write was reachable. If it was not, only an unchanged prior observation resolves; a changed value is unrelated and remains for a future explicit recovery procedure without consuming an attempt. Once a write was possible, an exact prior observation resolves as `prior-unchanged`; an exact target observation on either the same or a later boot restores the recorded prior; and absence on a later boot resolves as `consumed-unknown`. The latter means only that BootNext is now absent after a boot boundary, not that Windows booted or that firmware consumed the request. An independently written exact target is indistinguishable from the root's value; the deliberate rollback rule favors restoration of the immutable prior state, while every other changed value is preserved.
- Every attempt publishes a create-once pre-action record containing its root incident, root BootNext reference, both boot IDs, write frontier, direct observation, prior state, target number, action, tool evidence, and planned outcome. A separate final proof records command status and exact readback. Nonzero command status can resolve only when direct readback proves the planned state. Unreadable or unrelated observations, boot changes during an attempt, tool drift, variable replacement, and uncertain readback leave the incident recoverable without overwriting unrelated state. A transient restoration failure can retry from fresh observation; persistent failure is bounded by the 32-attempt incident limit and remains terminal to automatic recovery for a future explicit procedure.
- Windows recovery uses the existing root-linked attempt chain, root-captured service state, shared boot and repair locks, bounded attempt count, stale-attempt sealing, and stable-state-last publication. A completed stale attempt is published without replay; a failed attempt is retried only from a fresh direct observation. T-6.8 activates the T-6.7 public dispatcher routes through the shared production predicate.

## T-6.6 Decision Record

- Rechecked 2026-09-04 against limine-entry-tool 1.38.0. The installer reads its source from `/usr/share/limine/BOOTX64.EFI`, may skip the primary when its backup already matches that source, and updates an existing fallback only when fallback deployment is enabled or explicitly requested. Dormant unconfiguration therefore invokes the validated open inode for package-owned `/usr/bin/limine-install --no-efi-register --fallback`, binds both target hashes to the captured source hash, and directly requires zero embedded config checksums. The immutable root intent binds the pinned package version plus the path, device/inode, and SHA-256 hash of the installer, mkinitcpio wrapper, and enrollment-reset executable; every child revalidates that evidence immediately before execution.
- Limine's installer and mkinitcpio producer run pre/post hooks. Those hooks can restore and then re-enroll the primary when the restored original `ENABLE_ENROLL_LIMINE_CONFIG` value is `yes`; `limine-reset-enroll` itself restores or resets only the primary. Unconfiguration performs a final checked reset after both children, applies an ESP-wide durability barrier, then proves primary and fallback against the unchanged source before publishing its proof.

A stale mount at the private owned path is unmounted only when its `MAJ:MIN`, `vfat` type, and root agree with the mapped ESP; the underlying private mountpoint is validated after unmount because a live FAT root exposes its mounted mode. Loader validation opens the file once, checks the descriptor against the mapped `MAJ:MIN` and the PE magic, and never follows a symlink. Dangerous firmware cases that stay unexercised must be named in the release record.
- Consider a separate marketplace companion plugin rather than listing this repository directly. omarchyplugins.com is a community marketplace (HANCORE, repository `HANCORE-linux/omarchy-plugin-marketplace`, unaffiliated with 37signals) for Quattro-format plugins: a git repository plus `manifest.json` schema version 1, with kinds limited to six QML shell surfaces. Its user-level `omarchy plugin add` channel has no scripts or root access and cannot install this repo's command and hooks. A viable companion could use an ID outside `omarchy.*`, such as `peregrinus.secureboot`, with `bar-widget` and `menu` surfaces for Secure Boot status and reboot-to-Windows, while documenting the released package workflow as a prerequisite. `elynch303/security-scan` is precedent for a listed plugin with a manual `install.sh`. The marketplace baseline review-allows installers, sudo, and package-manager use; it auto-blocks NOPASSWD sudoers, curl-piped-to-shell, unpinned remote execution, and `/tmp` PID abuse, none of which this design uses. Open questions are maintainer acceptance of the pacman-hook-installing prerequisite and whether the discretionary `suite` listing type can carry the CLI tool alone.
