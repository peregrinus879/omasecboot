## T-6.2 Decision Record

- Producer lease admission and obligation derivation are pinned to `limine-mkinitcpio-hook` 1.38.0-1 and `limine-snapper-sync` 1.31.0-1. `limine-mkinitcpio-hook` owns `/usr/bin/limine-mkinitcpio`. UKI inventory and every repository hook derive package obligations from `/usr/lib/modules/*/modules.builtin`; `pkgbase` is not an authority.
- Only the package PreTransaction guard consumes `NeedsTargets`. Cleanup and final repair identify the validated live coordinator from the durable producer record and use its immutable pre-recorded target set rather than recomputing authority from post-hook input.
- Producer suppression and completion use the external coordinator's immutable record, exact identity, boot ID, process start time, and current ancestry. Top-level OmaSecBoot descendants use the separate transaction-token protocol.
- A separate Remove-only PreTransaction guard preserves the exact recovery command providers, pinned producer runtime dependencies, active watcher support, and supported configured hash utilities while lifecycle state is managed. The protected set includes `tar`, `libnotify`, `inotify-tools`, `b3sum`, and `xxhash` alongside the core repair stack. The hook consumes no target stream, runs before producer admission, and evaluates removal under both boot locks. Generic lifecycle mutation checks the canonical pacman database lock after acquiring those locks and immediately before publication, closing concurrent adoption after the removal hook returns. Successful OmaSecBoot package removal remains unavailable until the unconfiguration and package contracts land.
- Package target capture is bounded to 16,384 lines and 491,520 raw bytes so JSON escaping cannot exceed the 1 MiB control-document boundary; malformed or over-limit input is fully drained and blocks admission. Tests pin exact acceptance and one-line-over rejection at both limits. On 2026-09-02, the conservative installed inventory from every `linux-firmware*` package contained 6,620 `/usr/lib/firmware` paths and 363,115 bytes including leading slashes. Re-measure the actual ALPM target stream before T-6.8 activates producer automation.
- Active lifecycle blocks direct package changes to the four pinned producer packages because a PreTransaction query can prove only the installed version, not the incoming archive version. Disabled or pristine state remains the upgrade path; package dependency pins provide the normal release boundary.
- `producer_reconstruction_preflight()` is the only relaxed preflight and tolerates missing expected producer outputs only before fixed-registry reconstruction. Canonical artifact repair retains the strict `artifact_repair_preflight()` boundary.
- Producer lease publication requires stable `active` state. `unmanaged` and `disabled` package and Limine hooks remain no-state-write paths; `transition` and `recovery-required` fail closed unless validated producer recovery owns the transition. Public adoption remains blocked while lifecycle repair is unavailable so this dormant producer gate cannot strand a user in `active` state before unconfiguration and recovery ship.
- A proved snapshot-watcher descendant uses `service_policy: preserve-owner`; other producer contexts use `quiesce`. Full restore uses its exact process identity and an inode-bound upstream marker for specialized admission, while generic package admission remains marker-blocked and normal post-repair preserves the upstream-owned marker. Stale restore recovery scans for the exact root wrapper, sync script, and native worker, removes the marker pathname only while it still matches the recorded inode after durable incident publication under both locks, and leaves snapshot reconstruction marker-blocked against a new admission race. Same-boot stale transition reconciliation requires the recorded marker; cross-boot reconciliation and an existing validated recovery incident may accept absence after another clear process scan.
- An inherited FD 200 handoff reacquires the validated inherited open file description after reconstruction. If that reacquisition fails, recovery attempts the current canonical pathname's validated lock. Failure to acquire either lock leaves the durable transition unchanged for later reconciliation under both locks; the Limine post-hook returns a fatal status, so the calling mutation terminates without relying on the parent's unlocked descriptor.

## T-6.3 Decision Record

- Rechecked 2026-09-02: Arch ships `sbctl` 0.18-2 and upstream 0.18 remains the latest release. The tagged `enroll-keys` source permits `--partial` only for `db`, `KEK`, and `PK`; export writes those same three hierarchies, and no dbx writer exists. Firmware continuation remains pinned to `/usr/bin/sbctl` from that package and the exact confirmed `-m -f` plan.
- Incident recovery has an exhaustive operation map. A root with immutable producer evidence admits only `producer-recovery`; an `enroll-secure-boot` root without producer evidence admits only `firmware-recovery`. Other root operations cannot acquire a recovery attempt through these component gates.
- Firmware recovery takes no caller backup identifier. It validates the failed root's hashed `prior-lifecycle.json`, requires that document's exact completed transaction to be `activate-secure-boot-plan`, and derives the firmware-backup and confirmed-plan binding from that completed manifest. A root that failed before binding may acquire only that derived binding in its recovery attempt; later attempts inherit it exactly.
- Every attempt inherits the immediate predecessor's firmware ledger. A terminal pending record is classified against direct F0-F3 observation as `unchanged`, `verified`, or a coherent failure before any retry; technical readback uncertainty leaves it pending. A known state outside the permitted pre-write or post-write frontier is `failed`, terminal to automatic recovery, and retained for a future explicit recovery procedure. The existing six-record and two-per-hierarchy limits apply to the complete incident chain rather than restarting per attempt.
- Recovery keeps file restoration available only while the inherited ledger is empty and direct state remains F0. Otherwise it preserves the proved boot-artifact set. Every continuation repairs and proves EFI artifacts before a remaining firmware write and completes only after F3, a second EFI verification, and transaction-local firmware and schema-2 artifact proofs. The internal recovery capability is available, while firmware enrollment, the dispatcher, and consolidated repair remain closed.

## T-6.4 Decision Record

- Rechecked 2026-09-03: Arch ships `efibootmgr` 18-4 and upstream release 18 remains latest. The dormant writer is pinned to that package and `/usr/bin/efibootmgr`; the package hooks block its replacement during a managed lifecycle, package ownership is proved directly, and one validated open inode supplies the executable hash, final target query, and write. Revalidate package, release, option parsing, write width, and executable ownership before accepting another version.
- Linux efivarfs exposes four little-endian attribute bytes followed by payload. BootNext is accepted only as a root-owned, non-writable-by-group-or-others, six-byte regular file with attributes `NV|BS|RT` (`7`) and one little-endian UINT16. Absence is recorded distinctly. Any mount, metadata, size, attribute, identity, or read uncertainty blocks before mutation or leaves a published transaction recoverable.
- A root `windows-bootnext` transaction publishes a create-once schema-1 record containing the boot ID, exact persisted target, prior BootNext state, and pinned tool evidence before its only write. It then repeats the boot-ID, prior-value, executable-hash, and full target proof immediately before `efibootmgr -n`, and requires exact direct efivarfs readback plus another complete target proof. Command success alone never commits. Every post-publication failure remains `recovery-required` for T-6.5 resolution.
- The mutation predicate and public dispatcher remain closed. Hermetic tests exercise the internal boundary, command failure before and after effect, prior/target/tool races, malformed efivar data, mismatched readback, and interruption after write without claiming any real firmware mutation.
- The shared locks and package hooks serialize OmaSecBoot, Limine, package, and known producer activity, not arbitrary root processes or autonomous firmware changes. Immediate pre-write checks and a final BootNext read after the second target proof narrow that residual race but cannot exclude a non-cooperating external writer after the final observation.

## T-6.5 Decision Record

- Rechecked 2026-09-03: Arch still ships `efibootmgr` 18-4 and coreutils 9.11-2. efibootmgr 18's `-N` branch checks `is_current_entry(opts.delete_bootnext)`, where the option is a boolean set to one, so BootNext deletion incorrectly requires `Boot0001`. Recorded absence is restored by the one-path GNU `unlink` interface instead. The package hooks treat coreutils as a pinned producer; recovery proves package ownership, hashes and opens `/usr/bin/unlink`, records that tool plus the BootNext pathname, device, inode, and hash before mutation, re-proves those fields immediately before pathname-based unlink, executes the open tool inode, and requires direct absence readback. Recheck both package versions, the `-N` implementation, coreutils invocation, and efivarfs deletion behavior before accepting another version or changing this boundary. Because active lifecycle blocks a coreutils package transaction, revalidate and update the pin, package dependency, hooks, and tests while lifecycle is disabled or pristine before supporting a new coreutils release.
- A `windows-bootnext` root without a published BootNext record admits only `windows-recovery` and resolves as `not-published` without reading or writing efivarfs. With a record, immutable completed-phase evidence classifies whether the write was reachable. If it was not, only an unchanged prior observation resolves; a changed value is unrelated and remains for a future explicit recovery procedure without consuming an attempt. Once a write was possible, an exact prior observation resolves as `prior-unchanged`; an exact target observation on either the same or a later boot restores the recorded prior; and absence on a later boot resolves as `consumed-unknown`. The latter means only that BootNext is now absent after a boot boundary, not that Windows booted or that firmware consumed the request. An independently written exact target is indistinguishable from the root's value; the deliberate rollback rule favors restoration of the immutable prior state, while every other changed value is preserved.
- Every attempt publishes a create-once pre-action record containing its root incident, root BootNext reference, both boot IDs, write frontier, direct observation, prior state, target number, action, tool evidence, and planned outcome. A separate final proof records command status and exact readback. Nonzero command status can resolve only when direct readback proves the planned state. Unreadable or unrelated observations, boot changes during an attempt, tool drift, variable replacement, and uncertain readback leave the incident recoverable without overwriting unrelated state. A transient restoration failure can retry from fresh observation; persistent failure is bounded by the 32-attempt incident limit and remains terminal to automatic recovery for a future explicit procedure.
- Windows recovery uses the existing root-linked attempt chain, root-captured service state, shared boot and repair locks, bounded attempt count, stale-attempt sealing, and stable-state-last publication. A completed stale attempt is published without replay; a failed attempt is retried only from a fresh direct observation. The internal recovery predicate is available, but no public mutation or recovery dispatcher route is enabled until the later command-integration and activation units.

## Known Limitations

- Limine 12 can enforce BLAKE2B hashes on non-EFI loaded paths when Secure Boot and config checksum enrollment are both active. Omarchy boots UKIs through `protocol: efi`, which is exempt because firmware Secure Boot verifies EFI binaries. Limine 12 expects interface colors as `RRGGBB` values. Do not add automatic path-hash rewriting unless Omarchy moves to non-EFI loaded paths or explicitly enables that model; `status` warns about incompatible non-EFI path hashes and color values. As of 2026-09-02, Arch ships Limine 12.7.0. Its changelog adds Boot Loader Interface entry publication, entropy, and `terse`, without changing the 12.0.0 hash-enforcement, enrollment, `efi_boot_entry`, or color semantics. Re-audit the corresponding source before T-7 relies on 12.7.0 behavior.
- Omarchy Quattro 4.0 ships as pacman packages (`omarchy`, `omarchy-settings`) under `/usr/share/omarchy`. Limine settings live in `/etc/limine-entry-tool.d/{omarchy-defaults,omarchy-uki}.conf`, including `CUSTOM_UKI_NAME="omarchy"`; `/etc/default/limine` overrides both `/etc/limine-entry-tool.conf` and the `/etc/limine-entry-tool.d/*.conf` drop-ins (limine-entry-tool states this precedence in its config header) and carries `root=` plus this repo's Secure Boot settings. No Omarchy drop-in sets `ENABLE_VERIFICATION` or `ENABLE_ENROLL_LIMINE_CONFIG`, and the precedence keeps any drop-in from overriding them, so `/etc/default/limine` remains the repo's durable write target. Omarchy does not provision sbctl keys or expose an end-to-end Secure Boot workflow; its limine-entry-tool dependency provides scanner, enrollment, signing, and locking primitives that this repo integrates with. - Quattro supports free-space installation alongside Windows and documents `limine-scan`; limine-entry-tool 1.38.0 writes scanner entries as `protocol: efi` plus `path:`. OmaSecBoot's dormant handoff parser consumes efibootmgr 18's single raw `dp:` line for each verbose Boot option, rejects diagnostics and lowercase noncompliant Boot variable names, treats legal empty and End-Entire-only paths as non-targets, parses multi-instance paths without accepting them as supported targets, validates supported prefix-node lengths plus the `HD -> File(\EFI\Microsoft\Boot\bootmgfw.efi) -> End Entire` suffix, maps the mixed-endian GPT signature and geometry to one `vfat` ESP, and proves the loader's `MZ` header without writing it. A multi-instance path containing the exact Windows loader remains a failing candidate rather than being ignored. Limine 12.6.1 scans at most 128 BootOrder values, formats uppercase Boot variable names, compares the complete label with ASCII-only case folding, and does not filter inactive entries; target selection applies those rules and also requires the firmware active bit. Strict target state records Boot number, label, PARTUUID, and loader path and is revalidated independently before each dormant managed-block and BootNext write. The supported label set is 1-127 bytes in `[A-Za-z0-9 ._()+&-]`; localized labels, missing BootOrder records, BootOrder above 128 values, unsupported local transport nodes, ambiguous mounts, and HD/lsblk unit disagreement fail closed. Public Windows mutation remains blocked until the dormant transaction and recovery components are integrated into public commands; never create or relabel a firmware option automatically.
- A reusable ESP mount must be unique, identity-matched, free of same-device subroot aliases, and reached through a controlled path. One controlled `ro` or `rw` root mount may be reused without writing. A writable-mount loader read applies `O_NOATIME` to the already-bound descriptor through GNU `dd` and fails closed if the owner-or-`CAP_FOWNER` check or flag application fails. Linux rejects a second block-filesystem mount whose requested read-only state conflicts with the live superblock, so a controlled writable ESP is never routed to the owned-mount branch. An uncontrolled read-only root path is not read directly, and the mapped ESP is instead mounted `ro,noatime,dmask=0077,fmask=0177` under the locked, root-owned runtime path; a per-mount read-only alias over a live writable superblock can make that owned mount fail, and proof then fails closed. Uncontrolled writable, multiple, and subroot mounts fail closed. A stale mount at the private owned path is unmounted only when its `MAJ:MIN`, `vfat` type, and root agree with the mapped ESP; the underlying private mountpoint is validated after unmount because a live FAT root exposes its mounted mode. Loader validation opens the file once, binds the descriptor to the kernel `mnt_id` from `/proc/<pid>/fdinfo/<fd>` and the mapped `MAJ:MIN`, and compares the descriptor with the exact loader pathname before and after reading. Recheck efibootmgr raw output and diagnostics, Limine `efi_boot_entry` source, Linux block-superblock and `fdinfo` semantics, GNU coreutils inherited-descriptor flags, GNU `stat` descriptor fields, VFAT `O_NOATIME` behavior, and util-linux JSON keys before relaxing any parser boundary.
- HD short-form paths rely on point-in-time uniqueness across the current Linux block inventory; every dormant write repeats the GPT identity, geometry, FAT, mount, and loader proof. Firmware-only handles outside that inventory and device arrival after proof remain outside the target-identity claim. Expanded ACPI prefixes require three terminating ASCII strings, USB WWID prefixes carry 1-64 UTF-16 code units, and vendor-defined messaging prefixes accept only the 44-byte standard SAS shape and GUID; unknown messaging vendors fail closed.
- EDK2 commit `7835e580` packs Fibre Channel Ex and SAS Ex messaging nodes as 24 bytes. UEFI 2.11 specifies 24 bytes for Fibre Channel Ex but its example shows 20, while the SAS Ex table reports 32 bytes despite field offsets and EDK2 totaling 24. The parser follows EDK2's 24-byte emitted structures; recheck both node shapes against current EDK2, UEFI errata, efibootmgr output, and real firmware before relaxing or widening them.
