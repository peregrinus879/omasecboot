# Maintenance Ledger - OmaSecBoot

Primary sources, versioned compatibility findings with their recheck triggers, workaround removal triggers, active limitations, and deferred decisions. Read it before changing Secure Boot flow, sbctl tracking, Limine configuration semantics, pacman hooks, UKI handling, Windows behavior, or a deferred item, and re-fetch documentation-derived facts, package behavior, and version gates when acting on an entry. ## Compatibility Findings

### Limine

- Limine 12.8.0 (`common/lib/uri.c`, `common/protos/chainload.c`, `common/menu.c`, `common/lib/config.c` at tag v12.8.0, rechecked 2026-09-10): `secure_boot_active` holds only while firmware reports Secure Boot and the embedded config checksum is non-empty and matches; `hash_mismatch_panic` is then forced to yes and the editor is disabled. `chainload()` waives a missing hash for `protocol: efi`, but every present hash is verified. `uri_resolve()` rejects a suffix that is not exactly 128 hexadecimal characters. A mismatching hash panics when `hash_mismatch_panic` is set and otherwise stops at a confirmation prompt. The proof must therefore distinguish an absent hash from a malformed one and must propagate parser failure. Recheck these sources before accepting another Limine release or extending URI resolution.
- Omarchy's template sets `hash_mismatch_panic: no`; limine-entry-tool's shipped `ENABLE_VERIFICATION=yes` produces hashes of unsigned UKIs on a stock installation (TP3402VA A1 record, 2026-09-10). Activation invokes `limine-mkinitcpio` to regenerate the current OS entry under the managed settings. The later snapshot sync does not migrate stored historical hashes; the snapshot-history item below is a release blocker. Limine 12 expects interface colors as `RRGGBB`; the 12.7.0 and 12.8.0 changelogs retain the enrollment, `efi_boot_entry`, hash-enforcement and color semantics. Recheck the producer sources and Omarchy defaults when those packages change.
- Limine v12 searches executable-adjacent, `/boot/limine/limine.conf`, `/boot/limine.conf`, and `/limine/limine.conf` before the ESP-root `/limine.conf`; proof rejects those higher-priority candidates. Both bootable executables expose `++CONFIG_B2SUM_SIGNATURE++` followed by the enrolled 128-character BLAKE2B value. Upstream config enrollment can mask failure, modifies the primary in place, and pacman's `99-limine.hook` can write a raw fallback binary; sbctl issue #408 shows why a signed-then-modified binary is invalid, hence the staging-file build from `/usr/share/limine/BOOTX64.EFI`.
- Limine 12.6.1 scans at most 128 BootOrder values, formats Boot variable names in uppercase, compares the complete label with ASCII-only case folding, and does not filter inactive entries; the 12.7 and 12.8 changelogs leave those rules unchanged. Target selection applies them and additionally requires the firmware active bit.

### Omarchy Quattro

- Quattro 4.0 ships as pacman packages (`omarchy`, `omarchy-settings`) under `/usr/share/omarchy`. Limine settings live in `/etc/limine-entry-tool.d/{omarchy-defaults,omarchy-uki}.conf`, including `CUSTOM_UKI_NAME="omarchy"`; `/etc/default/limine` overrides both `/etc/limine-entry-tool.conf` and the drop-ins (limine-entry-tool states this precedence in its config header) and carries `root=` plus this tool's Secure Boot settings. No Omarchy drop-in sets `ENABLE_VERIFICATION` or `ENABLE_ENROLL_LIMINE_CONFIG`. Omarchy does not provision sbctl keys or expose a Secure Boot workflow. Its `00-omarchy-update-guard.hook` blocks direct `pacman -Syu` unless `OMARCHY_UPDATE_PACMAN=1` and sorts before `zz-*`, so hook ordering is unaffected. Verified against v4.0.2 (`346e69e1`).
- Quattro installs alongside Windows and documents `limine-scan`; limine-entry-tool 1.38.0 writes scanner entries as `protocol: efi` plus `path:`.
- Quattro's menu overlays the user-owned `~/.config/omarchy/extensions/omarchy-menu.jsonc` on the shipped menu per key and watches both files. Its parser strips only whole-line `//` comments; an inline comment or any parse failure silently drops every user entry. Guards run unprivileged in one batched bash process per reload and per open; inside it `omarchy-cmd-present` is a `command -v` function and `omarchy-pkg-present` answers from a `pacman -Q` snapshot, so `command -v` cannot distinguish a packaged command from a PATH copy. `omarchy refresh config omarchy/extensions/omarchy-menu.jsonc` replaces the user file with the shipped sample (keeping `<file>.bak.<epoch>`); `omarchy reinstall configs` copies `/etc/skel/.` over `$HOME` without a backup and runs `omarchy refresh limine`. Both drop the `system.windows` entry until the fragment is merged again.

### Limine tools and producers

- The `integrations/limine-entry-tool/0001-propagate-mkinitcpio-failures.patch` integration is bound to upstream 1.38.0 at `57092d98ba9d355f180b883dea0e9cfefeace8b1`; `source.json` records archive, input, patch and resulting-file digests. It propagates UKI and regular-kernel build/install failures through the per-kernel and aggregate producer result while retaining later-kernel processing, hook outcomes and cleanup errors. The offline real-shell contract suite covers both original masking and corrected outcomes, with external builders/installers controlled inside namespaces. Runtime admission remains stock 1.38.0-1.1 and integrated 1.38.0-1.2; no other build is admitted by that evidence. Shell results and a package build do not prove required-output completeness or safe active updates. Recheck on the next producer release and remove the patch when upstream satisfies the same result contract without it.
- `0002-propagate-native-failures.patch` on the same source makes detected required-input, directory, copy, attempted-hash, backup, configuration write/sync/move and addition-operand failures nonzero. It preserves genuine same-path/equal-content and recent-backup behavior, rejects malformed/disputed hashes instead of accepting an empty or disputed value, uses literal argv for hash/sync and logger messages, and scopes scanner unmount cleanup around newly propagated exceptions. `source.json`'s native contract binds all 19 compiled Java inputs. `make test-native` compares actual original/patched publisher classes; its Config is supplied by the fixture, so it does not establish full configuration admission, actual FAT selection or the full scanner path. Detected errors may leave partial copied artifacts or a temporary configuration; atomic multi-file publication, native deletion guarantees, complete output coverage and lifecycle integration remain separate. Missing optional hash-tool availability retains upstream policy. Recheck on the next producer release; remove when upstream passes the same failure/no-op contracts.
- The integration recipe builds development 1.38.0-1.3 with both patches, preserving upstream package dependencies, files, modes and symlinks. Its x86_64 GraalVM build against the stable Omarchy mirror, all 56 payload entries and all 19 compiled source hashes were checked in a disposable Arch container on 2026-09-12. Isolated packaged-ELF checks cover version and missing addition operands; actual FAT/boot and aarch64 acceptance remain pending. The build is not yet a runtime activation candidate. The container must initialize its own Arch keyring before package updates, as the normal Omarchy builder does; pacman's successful exit alone can otherwise hide a keyring scriptlet failure. Revalidate source, toolchain, payload and target-channel profile before changing the recipe or admitting the build.
- limine-entry-tool and limine-snapper-sync use FD 200 and `/run/lock/boot-partition.lock`, but several audited wrappers continue after `mutex_lock` failure. Full `limine-snapper-restore` invokes `limine-snapper-sync --restore --no-mutex` without a parent shared lock; its wrapper creates the restore marker before pre-hooks, removes it through an `EXIT` trap, and the native worker writes `restored` without replacing the inode. Stopping `limine-snapper-sync.service` does not quiesce Snapper plugins, transient units, or the cleanup service's `ExecStopPost`. Pacman PostTransaction hooks do not run after a failed transaction.
- limine-entry-tool 1.38.0's `run_boot_hooks` (`limine-common-functions`) executes every regular executable under `/etc/boot/hooks/pre.d/` and `post.d/` directly, so the hooks inherit the caller's environment, including the owning transaction's token that the Limine hooks' ownership proof reads, plus every `VAR=value` the tool's config loader exports; a hook exit status below 100 is a warning and 100 or higher aborts the caller. Recheck both facts when limine-entry-tool changes.
- Current Limine packages provide `/etc/boot/hooks/pre.d/10-limine-reset-enroll`, `/etc/boot/hooks/post.d/89-warn-missing-file-hashes`, and `/etc/boot/hooks/post.d/90-limine-enroll-config`; the warning hook sorts before `zzz-omasecboot-sign` and stays silent for EFI-exempt UKI builds. limine-entry-tool reads sbctl state through JSON.
- limine-entry-tool 1.38.0's `limine-install` deploys the fallback loader `/EFI/BOOT/BOOTX64.EFI` when `ENABLE_LIMINE_FALLBACK` is `yes`, when called with `--fallback`, or when the setting is unset (an empty value counts as unset) and the loader is missing; with `no` it never touches it (`usr/bin/limine-install` at tag 1.38.0). The setting resolves through four layers, the last assignment winning: `/usr/share/limine-entry-tool.d/*.conf`, `/etc/limine-entry-tool.conf`, `/etc/limine-entry-tool.d/*.conf`, then `/etc/default/limine` (`load_config` in `limine-common-functions`). Omarchy's drop-in `omarchy-defaults.conf` sets `yes`, and the shipped `limine-entry-tool.conf` comment recommends disabling it under Secure Boot. Observed 2026-09-10 on the Vivobook TP3402VA (Omarchy 4.0.3 with Windows on its own ESP, `nvme0n1p1`, and Omarchy's on `nvme0n1p6`): `/etc/default/limine` carried `ENABLE_LIMINE_FALLBACK=no` as installed (H confirmed the operator did not write it), no fallback loader existed, and setup's activation preflight refused because both loaders were required (fourth run, A2). The tool now manages the fallback only when the effective policy deploys it or the file exists, refuses a deploying policy whose loader is missing, and unconfiguration adds `--fallback` only when its intent recorded the loader as managed (intent and proof schema 2). Which installer step writes `no` was not traced (no public Omarchy ISO repository was found); recheck `limine-install`, `load_config`, and the Omarchy drop-ins before accepting another limine-entry-tool or Omarchy release.
- limine-entry-tool 1.38.0's installer reads its source from `/usr/share/limine/BOOTX64.EFI`, may skip the primary when its backup already matches the source, and updates an existing fallback only when fallback deployment is enabled or explicitly requested. Its pre/post hooks can restore and then re-enroll the primary when the restored `ENABLE_ENROLL_LIMINE_CONFIG` value is `yes`; `limine-reset-enroll` restores or resets only the primary.
- limine-mkinitcpio-hook 1.38.0 obtains each kernel name from package ownership of `/usr/lib/modules/*/modules.builtin`; its defaults set `ENABLE_UKI=no`; a missing, empty, or invalid `CUSTOM_UKI_NAME` uses the machine ID, which OmaSecBoot mirrors. Its per-kernel path returns success after a failed UKI build and the outer loop continues, so producer exit status cannot prove that every expected UKI exists; OmaSecBoot therefore signs and tracks what it discovers rather than deriving an inventory. Re-audit the producer script, defaults, ALPM triggers, and masked-failure behavior before accepting another version.
- limine-snapper-sync 1.31.0 writes manifest schema 1.3.0 to `${ESP_PATH}/${machine-id}/limine_history/snapshots.json`. Re-audit the history path and hash suffixes before accepting another version.
- limine-snapper-sync 1.31.0 (`ImageDetail.getSnapshotLine`, `KernelReader.convertToImageDetail`, `LimineWriter.buildBootNode`, `Hash.hasCorruption`, and `SnapshotManager` at `0df30174795c47bc3f85fe701de92c308aeee840`, rechecked 2026-09-10) retains path hashes in its manifest and checks file content against the hash in the history filename. A normal sync, with or without `--no-force-save`, does not migrate those identities. In-place signing can both leave Limine hashes stale and make history look corrupted to the producer. The producer has no `ENABLE_VERIFICATION` setting. Its `--add ID` captures current OS artifacts and is not a historical import; `--remove` retires boot records and unshared history files while preserving Btrfs snapshots. A migration must preserve historical kernel/root association and update every stored representation, including restore entries. Older UKIs with embedded `.cmdline` additionally need an explicitly verified transformation or compatible historical rebuild, because systemd-stub can ignore externally supplied snapshot command lines under Secure Boot. Recheck on the next producer/systemd change; remove the limitation only after a producer-compatible migration and subsequent boot/restore tests pass.
- omarchy-pkgs commit `520dd5c` (2026-09-04, "Repair aarch64 package coverage") raised both producers to pkgrel 1.1: the aarch64 build downloads Gradle 9.7.1 and the make-dependencies split by architecture, while the x86_64 inputs (the upstream tag source hash, the GraalVM archive, and the build steps) are unchanged. A packaging-only rebuild, like sbctl 0.18-2 below; the exact pins moved to the new releases. Recheck the recipe diff and the payload the same way when the Omarchy repository publishes another pkgrel.
- `zz-sbctl.hook` runs `sbctl sign-all -g`, which asks sbctl to generate or rebuild UKI bundles; with `CUSTOM_UKI_NAME="omarchy"` and limine-entry-tool building UKIs while sbctl's own `sb_sign()` is disabled this is a no-op. Watch item: re-audit if that hook or the `-g` semantics change.

### sbctl

- sbctl 0.18's `status` command discards individual firmware-mode read errors when constructing its JSON booleans. Status therefore validates the JSON shape and independently checks the same direct mode observation used by enrollment; failed reads or disagreement are unverified, not a boolean default. Its stale-tracking observation also requires a complete database read when the store exists, because a successful CLI view can omit invalid or missing outputs; a failed database read cannot be rescued by that partial view. An absent store requires readable/searchable ancestry and an empty successful CLI observation. Recheck when sbctl's status/list-files behavior or either direct reader changes.
- sbctl 0.18-2 (a packaging-only rebuild of the 0.18 tag) ignores `sign -s` for already-signed files, so snapshot UKIs can be signed but untracked; `save_sbctl_file_entry` writes the expected `SigningEntry` directly into the file database. Upstream fixed this on master in commit `ae9c8958` (issue #482). Remove the direct-registration workaround only after a fixed tagged release reaches Arch; verify with `pacman -Q sbctl` and the upstream release list.
- Its config parser accepts YAML or JSON and defaults `files_db` to `/var/lib/sbctl/files.json`; without `/etc/sbctl/sbctl.conf`, an existing legacy `/usr/share/secureboot` directory selects `/usr/share/secureboot/files.db`. `list-files --json` prints an array of entries carrying `file`, `output_file`, and `is_signed` (`cmd/sbctl/list-files.go` at tag 0.18: `JsonFile` values through `JsonOut`), and skips an entry whose output file fails verification; the database it reads is an object keyed by path whose values carry `file` and `output_file` (`SigningEntries`). OmaSecBoot reads exactly those two shapes and merges database rows into cleanup because the CLI view can be incomplete.
- sbctl 0.18 owns the layout under `/var/lib/sbctl`, and setup creates nothing there itself. `create-keys` (`cmd/sbctl/create-keys.go` at tag 0.18) runs `CreateDirectory` for the key directory and the GUID's directory (`MkdirAll` with `os.ModePerm`, 755 under the root umask), `CreateGUID` (0644, only when absent), and then `backend.CreateKeys` plus `SaveKeys` (hierarchy directories 755, every key and certificate 0400) only while `CheckIfKeysInitialized` (`keys.go`) finds one of `keys/PK`, `keys/KEK`, and `keys/db` missing; with all three present it prints "Secure boot keys have already been created!" and exits 0 without writing a key. Observed 2026-09-09 on the Vivobook TP3402VA, third run: setup had pre-created those directories so that rollback could record the key files as absent, sbctl treated them as a created key set, setup refused the partial result, and the rollback removed only files, so the empty directories survived for the next attempt. Setup now runs `create-keys` under umask 022, so the modes are the ones above whatever the caller's shell set, and records the absent directories themselves (the `absent-directory` backup kind: the deepest existing ancestor of the key directory is validated, the directory below it, or each hierarchy directory when `keys` exists, is recorded, and the GUID is recorded as an absent file when its directory exists) and rollback removes them with everything below; a hierarchy directory that exists while no key file does is refused before the transaction, by name. `list-files` and `verify` read the file and bundle databases through `ReadOrCreateFile`, which creates `/var/lib/sbctl` and a zero-length `files.json` or `bundles.json` on a keyless machine, so the tool's own `status` and the acceptance recorder leave a 755 state directory behind before setup (observed in the second run of 2026-09-09); an existing directory is held to the control-directory rule (owner, no group or other write) and 0400 keys classify as complete.
- efivarfs marks every variable outside its removable list immutable at inode creation (`fs/efivarfs/vars.c` `variable_validate`, `super.c` `efivarfs_get_inode` at v7.2: Boot####, BootOrder, BootNext, Driver*, Con*, Err*, Lang, PlatformLang, OsIndications, Timeout, and the crash GUID are removable; PK, KEK, db, and dbx are not). sbctl 0.18 `enroll-keys` runs `sbctl.CheckImmutable` before any write unless `--export` or `--ignore-immutable` is given (`enroll-keys.go`, `util.go`, `chattr.go`); the check reads the real attribute (`main.go` builds `afero.NewOsFs()`, a pointer, so the value-typed test hook in `IsImmutable` never matches) and exits 1 with "File is immutable" per file plus "You need to chattr -i files in efivarfs". Probed unprivileged on the development laptop (ASUS GU605CR) on 2026-09-10 (sbctl 0.18-2, kernel 7.2.3-arch1-3, `lsattr` showing `i` on all four variables): `sbctl enroll-keys -m -f --partial db` refused all three before touching anything; with `--ignore-immutable` it proceeded to the key read. sbctl's write layer is built with `efivarfs.NewFS().CheckImmutable().UnsetImmutable()` (`main.go`; go-uefi `efivarfs/fswrapper/fswrapper.go` at the pinned commit `69fb7dba244f` clears the attribute with `attr.UnsetImmutable` before each write), so enrollment passes `--ignore-immutable` on every partial write and never runs `chattr` itself; the flag only skips the 2021 pre-check (upstream PR #48). The enrollment suite's stub refuses an unflagged partial write the same way. Recheck `enroll-keys.go`, `util.go`, `main.go`, the go-uefi pin, and the kernel's removable list before accepting another sbctl or kernel release.
- sbctl 0.18 landlock (`lsm/lsm.go`, on by default) grants every command read-write access to the key directory's parent and efivarfs plus the GUID and both databases, all ignored when missing; `create-keys` adds the parent of that parent (`/var/lib`), `enroll-keys --export` adds the working directory and writes `db.esl`, `KEK.esl`, and `PK.esl` there at 0644 before the umask (setup runs it inside the plan directory under umask 077), `sign` in place adds the target file with truncation, `verify` adds the ESP, and `list-files` and `verify` add the database's recorded files. `enroll-keys --partial` does not require Setup Mode itself (`RunEnrollKeys`); the tool proves Setup Mode before each write. Recheck `lsm/lsm.go`, `create-keys.go`, `enroll-keys.go`, `sign.go`, `verify.go`, and `list-files.go` before accepting another sbctl release.
- The tagged `enroll-keys` source permits `--partial` only for `db`, `KEK`, and `PK`; export writes those same three hierarchies; no dbx writer exists. Bare `-f` includes firmware-builtin db and KEK, never PK; `-m` adds Microsoft db and KEK; `--export esl` performs no firmware write. Recheck the package source, config schema, executable ownership, default paths, ESL behavior, and partial-write semantics before supporting another sbctl release or a custom key backend.
- efitools 1.9.2 authenticated replacement uses a future-year timestamp marked FIXME, so it is not an approved recovery primitive. `sbctl reset` is a PK-removal operation, not factory restoration.

### Firmware modes

- AuditMode and DeployedMode are UEFI 2.5 variables that the specification defines together. Observed 2026-09-09: the ASUS Vivobook TP3402VA (AMI BIOS TP3402VA.307 of 2024-10-17) exposes neither, while the ASUS ROG Zephyrus GU605CR exposes both; `AGENTS.md` owns the acceptance rule. Recheck if an acceptance machine is refused for exposing only one of the two, or reports either with a payload other than one byte.
- On the TP3402VA a PK-only delete from the key menu left KEK and db in place with SetupMode reading 1 (A3-setupmode records of 2026-09-09). Firmware that clears more than the PK, or reinstalls its default keys on the next boot, has not been observed yet; the checklist records either as a refusal for that firmware.
- TP3402VA BIOS 307, A3 at 2026-09-10T12:19:02Z: db and KEK commands returned 0 with verified readback; PK returned 0, the trust databases compared exact against the plan and dbx against the backup, but SetupMode remained 1 and the PK readback was recorded failed. The reboot record at 12:32:09Z showed SetupMode 0 with Secure Boot off. This is a delayed observation, not proof of its cause: UEFI 2.11 section 32 requires immediate transition to User Mode after successful PK enrollment. Historical PK reconciliation retains strict F3 and the original sealed failure. Revalidate on a firmware, kernel, or sbctl change and during the recovery hardware row; same-boot completion with a pending mode remains a separate design.

### efibootmgr and efivarfs

- efibootmgr 18's `show_var_path()` emits one raw device-path line with the literal prefix `      dp: `, one space between bytes, ` / ` only between nodes, and no trailing separator; optional data uses one `    data: ` line with the same spacing. `-n` accepts a hexadecimal option up to `0xffff` and writes BootNext as a two-byte value. `-N` sets a boolean but the deletion branch passes that value to `is_current_entry()`, so deletion incorrectly requires `Boot0001`; recorded absence is restored with `rm` instead. Recheck raw output, option parsing, write width, and the `-N` implementation before raising or removing the version floor.
- Linux efivarfs exposes four little-endian attribute bytes followed by the payload. The shared locks and package hooks serialize OmaSecBoot, Limine, package, and known producer activity, not arbitrary root processes or autonomous firmware changes; immediate pre-write checks and a final read after the second target proof narrow that residual race but cannot exclude a non-cooperating external writer after the final observation.

### ESP mount and loader read

- A reusable ESP mount is the single whole-filesystem `vfat` mount of the mapped device; more than one fails closed. Without one, the mapped ESP is mounted `ro,noatime,dmask=0077,fmask=0177` under the locked, root-owned runtime path; Linux rejects a second block-filesystem mount whose read-only state conflicts with the live superblock, so a live writable mount is always the reused path. The loader read applies `O_NOATIME` through GNU `dd` and fails closed if the owner-or-`CAP_FOWNER` check or the flag application fails. Recheck efibootmgr raw output, Limine's `efi_boot_entry` source, and the block-superblock semantics before accepting other versions.
- HD short-form paths rely on point-in-time uniqueness across the current Linux block inventory; every guarded write repeats the GPT identity, geometry, FAT, mount, and loader proof. Firmware-only handles outside that inventory and device arrival after proof remain outside the target-identity claim.
- util-linux 2.42.3's `blkid --probe` exits 0 whenever the probe found any value, counted before the `--match-tag` filter, and 2 only when it found none (`misc-utils/blkid.c`, `lowprobe_device`); low-level probing reports partition-entry details for a partition device, so on 2026-09-09 every GPT partition of the Vivobook TP3402VA answered status 0 with empty output for the `BitLocker` filter, which the preflight then reported as inconclusive. The 2026-08-30 check against a generated FAT image returned status 2 for the same filter because an image has no partition entry, and `vfat` with status 0 for the `vfat` filter. The preflight now counts both answers as negatives after a direct read of the device succeeds, and anything with stderr output or an unexpected type value as unknown. `blkid` identifies BitLocker format but not protection state or edition. Recheck `lowprobe_device` and the partition-details flag before accepting another util-linux release.

### Windows

- Windows preparation reuse is process-local and bound to fresh validated firmware inventory, the canonical block inventory including PARTUUID, tri-state detection and per-device results. util-linux's explicit `PATH,MAJ:MIN,TYPE,PARTUUID,PARTTYPE,RM,TRAN,SUBSYSTEMS` JSON shape was checked on 2.42.3 on 2026-09-10. Missing or ambiguous partition IDs disable reuse, not detection. Changed or unknown observations discard previous answers. Recheck the collection contract whenever the lsblk columns, firmware parser, or loader inspection changes; no cross-invocation acknowledgment is persisted.
- Microsoft documents Device Encryption decryption through Settings on Home and no Home suspension workflow; Pro, Enterprise, and Education have documented BitLocker suspension; managed devices require administrator approval. Windows 11 24H2 broadens automatic-encryption eligibility without making encryption universal.
- UEFI BootNext is a one-boot request that firmware deletes before transferring control, so later absence cannot distinguish consumption from another deletion and does not prove Windows booted. Limine's `efi_boot_entry` requests a direct firmware handoff; it proves nothing about Windows boot, measurements, PCR7, or BitLocker recovery. Firmware and Windows certificate servicing after replacing the OEM PK are limitations, not benefits.

### Packaging and CI

- pacman searches configured hook directories (`/etc/pacman.d/hooks/` by default) after the system directory, and a same-named hook in a later directory replaces the earlier one (pacman.conf(5), `pacman-conf HookDir`, verified 2026-09-07); ordering across directories is by filename, so `zz-sbctl` < `zzz-omasecboot` holds.
- Stock pacman 7.1.0.r9.g54d9411-2 / libalpm 16.0.1 (`lib/libalpm/{hook,trans}.c` and `alpm.h` at [54d94116164b0b2202c6061c4a59c6f3e70820d8](https://gitlab.archlinux.org/pacman/pacman/-/tree/54d94116164b0b2202c6061c4a59c6f3e70820d8), rechecked 2026-09-12): PreTransaction `AbortOnFail` includes hook dependency and command-launch failures. PostTransaction hook failures do not make `alpm_trans_commit` fail, and the public hook-done event has no result field. Identical pre/post trigger sections use the same native transaction matcher; `NeedsTargets` is sorted and deduplicated. `make test-pacman-contract` exercises these contracts with real pacman in fixture-only Bubblewrap namespaces, including early failure, signals, changed/deleted post-hooks and a fresh retry after failure. The fixture's expected/terminal records demonstrate the mechanism, not an implemented OmaSecBoot lifecycle protocol. Recheck the matcher, hook-directory precedence, execution and finalization behavior on a pacman update or a change to any paired hook definition; do not treat CLI exit 0 or missing self-registration as package-producer success.
- Pacman's `-Ql` lists package declarations even when a module directory or `modules.builtin` is missing; directory-only ownership is not a kernel declaration. However, the same version's `be_local.c` skips invalid database entries after logging an error, and an unreadable/missing package file list can produce an empty partial listing with exit 0. The stock-pacman contract suite covers both cases. A required-output reader must require a complete, valid query with no unclassified diagnostics, not exit status alone or surviving-file ownership lookup. Recheck on a package-database reader change; no direct-database fallback is selected for the proof path.
- systemd's `21-systemd-tmpfiles.hook` applies a tmpfiles declaration after every install or upgrade that touches `usr/lib/tmpfiles.d/*.conf`; `ensure_state_layout` also creates the state directory on first use.
- Arch packaging guidance discourages informational install scriptlets; add one only if a release needs a real `post_upgrade` migration.
- Create-once incident publication requires coreutils 9.5 or newer for `mv --update=none-fail` and uses `--no-copy` so an unavailable same-filesystem rename fails closed. Recheck the manual, `mv.c`, and the Arch package before lowering this floor or replacing the primitive.
- GitHub's runners expose a writable efivarfs inside the job container, so mount state is not a usable disposable-root signal there. The `archlinux:base-devel` image sets `NoExtract` for documentation, so `tests/package-root.sh` removes those rules before `pacman -Qkk` can verify the packaged README. Re-check both if the runner image or the workflow changes.

## Deferred Items

- Release blocker: producer-compatible snapshot migration, complete required-output proof, and destination-root restore continuity. Current discovered-file proof does not establish all required OS outputs. The existing restore pre-hook runs before the native worker selects its final target; a post-hook in the running root does not establish the next root's compatible code, hooks, signing authority, configuration, or recovery records. Integrations are maintained as pinned patches and package recipes in this repository. Accept them only with real-tool contract tests and disposable boot/restore evidence; warnings or deleting snapshots do not close these obligations.
- Release blocker: supported active-lifecycle updates through Omarchy's normal package workflow. Currently, the transition guard refuses changes to the three pinned producer packages while `active`, and leaving `active` requires Secure Boot off. The supported launch needs a controlled update path without that routine firmware round trip, preserving package ownership, boot/recovery evidence and forward schema continuity. Resolver floors remain in PKGBUILD; incoming package versions/bytes require transaction-bound admission rather than cache or sync-database guesses. For ordinary fixed-producer transactions, the real-pacman contract suite establishes the basis for paired pre-hook expectations and a producer runner that records actual exits. The runtime pairing, canonical hook-set proof, complete output proof and post-pacman Omarchy completion check remain to implement; changing the incoming producer/hook set is a separate admission problem. A custom pacman package is not assumed necessary. Revalidate both current stable/RC and edge package profiles when implementing this path.
- Consider a separate marketplace companion plugin rather than listing this repository directly. omarchyplugins.com is a community marketplace (HANCORE, repository `HANCORE-linux/omarchy-plugin-marketplace`, unaffiliated with 37signals) for Quattro-format plugins: a git repository plus `manifest.json` schema version 1, with kinds limited to six QML shell surfaces. Its user-level `omarchy plugin add` channel has no scripts or root access and cannot install this repository's command and hooks. A viable companion could use an ID outside `omarchy.*`, such as `<vendor>.secureboot`, with `bar-widget` and `menu` surfaces for Secure Boot status and reboot-to-Windows, while documenting the released package as a prerequisite. `elynch303/security-scan` is precedent for a listed plugin with a manual `install.sh`. The marketplace baseline allows installers, sudo, and package-manager use; it blocks NOPASSWD sudoers, curl-piped-to-shell, unpinned remote execution, and `/tmp` PID abuse, none of which this design uses. Open questions are maintainer acceptance of the pacman-hook prerequisite and whether the discretionary `suite` listing type can carry the CLI tool alone.
- No supported reset exists for a recorded firmware backup or enrollment plan that stops validating: `setup` refuses to replace recorded evidence, `unconfigure` needs `active`, and deleting `/var/lib/omasecboot` breaks the lifecycle references. Decide before `v1.0.0` whether a guarded plan-retirement command is warranted or whether the README's stop-and-report guidance is the release position.
- Full-restore durability: lifecycle, tracking, settings, recovery evidence, and the sbctl keys live on the root subvolume, and `limine-snapper-restore` replaces that subvolume with the snapshot's copy while the ESP and firmware stay current. Observed 2026-09-09 on the ASUS Vivobook TP3402VA with the lifecycle unmanaged: restoring a snapshot older than the package install removed `/var/lib/omasecboot`, the package, its hooks, and `/var/lib/sbctl` from the next boot's root, and the restore copied that snapshot's UKI from `limine_history` back to `/boot/EFI/Linux`; the post-hook can sign that copy only because the running root still holds the tool. With the lifecycle active, such a restore leaves a system that boots but cannot sign its next UKI; the README documents the recovery route. Open: whether the Limine pre-hook should refuse or warn when the restore target predates activation, and whether keys and records belong on a subvolume the restore does not replace. A restore of a snapshot taken after activation has not been traced yet (checklist row A9).
- Windows targeting accepts device-path prefix nodes and resolves through the HD node's identity and geometry; full-device-path and HD-short-form entries have not been compared on real firmware. Verify both resolve to the same partition before strengthening the target-identity claim.
- Firmware that clears KEK, db, or dbx together with the PK is refused at enrollment, because the plan comparison requires them unchanged from the backup, although the recorded plan already carries every entry the firmware held. Supporting it means enrolling the stored plan ESLs through a write path that does not regenerate from the cleared firmware (verify sbctl 0.18's custom-key option against its source before designing), an additional F0 frontier for absent KEK and db, recovery-registry updates, and hardware validation. Trigger: a Tier A or Tier B machine whose PK delete clears more than the PK.
- Microsoft's 2023 certificate servicing writes db and dbx through Windows Update (and would write KEK while the OEM PK is present), and firmware updates change db or dbx. Before enrollment the changed set is refused with the difference named; after enrollment the OmaSecBoot-signed Linux boot path is unaffected (Windows' own boot manager is subject to whatever dbx it received), but `setup` and `enroll` observe state 3 and refuse at the boundary. Decide together with the plan-retirement item whether a guarded plan refresh that accepts byte-exact, separately verified Microsoft additions is warranted before `v1.0.0`. Trigger: any acceptance record showing db or dbx different from the plan after Windows booted.
- CI duration of the enrollment suite: the hermetic job allows 90 minutes since 2026-09-09. The suite took 52 minutes on the 2026-09-08 run and exceeded the earlier 60-minute limit on the 2026-09-09 run of `344d05c` after the absent-mode cases were added. When the job passes 75 minutes, split the suite across two matrix entries (the runner accepts one `ENROLLMENT_TEST_CASE`; a case-list filter is needed first) rather than raising the limit again.
