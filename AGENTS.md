# AGENTS.md - OmaSecBoot

OmaSecBoot: sbctl signing, Limine enrollment, pacman and Limine hooks, and a Windows BootNext handoff for Omarchy.

Naming boundary: `OmaSecBoot` is the product name; `omasecboot` is the sole user command and machine-facing namespace. The command, library, state directory, hooks, the Windows opt-in record, the managed `limine.conf` block, and the Limine hook protocol all use it.

## Load Map

- `README.md` - operator documentation: requirements, installation, lifecycle, setup, Windows, hooks, commands, recovery, undo, troubleshooting, boundaries.
- `docs/maintenance.md` - the on-demand ledger: primary sources, versioned compatibility findings with their recheck triggers, workaround removal triggers, active limitations, and deferred decisions. Read it before changing Secure Boot flow, sbctl tracking, Limine configuration semantics, pacman hooks, UKI handling, Windows behavior, or a deferred item; re-fetch changeable facts at change time.
- `docs/omarchy-integration.md` - what remains outside this repository (omarchy-pkgs recipe, Omarchy wrappers, menu entries, manual page) and the claim boundaries those pages keep.
- `docs/release-checklist.md` - the hermetic, package, and privileged hardware evidence a release tag requires, the acceptance procedure, and where reviewed records live.

## Key Files

- `bin/omasecboot` - entry point and command dispatcher
- `lib/*.sh` - one module per concern (see Architecture)
- `PKGBUILD` - Arch package recipe: `any` architecture, resolver-floor dependencies, `make DESTDIR=... install` payload; the omarchy-pkgs recipe pins the tagged archive hash
- `omasecboot.tmpfiles` - declares the state directory and the repair lock, installed as `/usr/lib/tmpfiles.d/omasecboot.conf`
- `pacman-hooks/00-omasecboot-removal-guard.hook` - the removal guard: refuses removal of `omasecboot` or a runtime dependency unless the lifecycle is verified `disabled` or pristine
- `pacman-hooks/00-omasecboot-transition-guard.hook` - the transition guard: admits or refuses transactions that touch boot paths or producer packages
- `pacman-hooks/zzz-omasecboot.hook` - the repair hook: completes the package producer's repair after `zz-sbctl.hook`
- `limine-hooks/000-omasecboot-guard` - the Limine pre-hook: lifecycle and shared-lock ownership validation
- `limine-hooks/zzz-omasecboot-sign` - the Limine post-hook: owned suppression or serialized producer repair
- `omarchy/omarchy-menu.jsonc` - reference fragment for the Quattro "Reboot to Windows" menu entry
- `Makefile` - `package` (build from tracked files), `install` (package staging only; refuses a live root and any uninstall), `test` (the aggregate)
- `.github/workflows/ci.yml` - lint, one job per hermetic suite, the package build, and the privileged container check
- `tests/*.sh` - nineteen hermetic suites run by `make test`, plus `tests/package-root.sh` (root, disposable container only; CI runs it) and `tests/acceptance-capture.sh` (root, real hardware; records one file per checklist row)
- `tests/lib/harness.sh` - the suites' scratch directory, failure reporter, cleanup, and the preflight-free transaction helper

## Architecture

The dispatcher sources the modules in this order and each owns one concern:

- `common.sh` - constants, output helpers, quiet mode, control-file validation, both locks, the pacman helpers, `json_is`, the ESP and efivarfs predicates
- `lifecycle.sh` - versioned state, transaction manifests, incident seals, recovery context, stale reconciliation
- `records.sh` - domain record schemas, references, validators, and the once-only record persister
- `software.sh` - software recovery for restore-policy roots
- `checks.sh` - root, dependency, EFI mode, ESP mount, and gum checks; the lifecycle activation environment
- `discover.sh` - EFI artifact discovery, sbctl configuration and tracked-file discovery
- `sign.sh` - Limine settings, config-checksum enrollment, signing and tracking, artifact proof, unconfiguration and its recovery
- `producers.sh` - producer admission, leases, the fixed reconstruction and recovery registry, the pacman and Limine hook entry points
- `enroll.sh` - firmware backup, trust plan, setup-state classification, guarded enrollment, firmware recovery
- `windows.sh` - Windows target proof, encryption preflight, the managed `limine.conf` block, BootNext mutation, Windows recovery
- `status.sh` - the `status` display, including the lifecycle line

## Dependencies

Runtime: sbctl, jq, openssl, gum (interactive commands only), efibootmgr, util-linux, diffutils, limine, and the base toolchain (bash, coreutils, findutils, gawk, grep, pacman, systemd). Declared package dependencies: the same plus `limine-mkinitcpio-hook` and `limine-snapper-sync`, which supply the Limine tools the hooks and unconfiguration run. `PKGBUILD` declares resolver floors only; activation enforces the three exact producer package versions and the efibootmgr floor at runtime.

## Terminology

One name per concept, in code, tests, and documentation:

- Lifecycle states: `unmanaged`, `disabled`, `active`, `transition`, `recovery-required`. "Pristine" means no lifecycle record exists (no state directory, or no `lifecycle.json`); it is the state a fresh install has and the only state besides verified `disabled` from which the package may be removed.
- Hooks: the removal guard, the transition guard, the repair hook (pacman); the Limine pre-hook and post-hook.
- Locks: the shared boot lock (`/run/lock/boot-partition.lock`, FD 200, shared with limine-entry-tool and limine-snapper-sync) and the repair lock (`/var/lib/omasecboot/repair.lock`, FD 201). "Both locks" means both.
- The restore marker: `/run/lock/limine-snapper-restore.lock`, created by limine-snapper-sync's full restore.
- Producer: an external process that regenerates boot artifacts through the hooks (the package transaction, limine-entry-tool, limine-mkinitcpio, limine-snapper-sync, and a full restore).
- Trust plan: the confirmed db, KEK, and PK set derived from a firmware backup; the enrollment is its application.
- The Windows opt-in record (`/var/lib/omasecboot/windows-enabled`) and the managed Windows block in `limine.conf`.
- Recovery operations: producer, firmware, Windows, software, and unconfigure recovery, one per root operation.

## Invariants

- Durable lifecycle state distinguishes the five states above. A top-level mutation writes its root-owned manifest and backups before mutating, commits stable state last, and leaves `recovery-required` when rollback fails. Existing unrecorded configurations require explicit adoption; never infer their originals or permit adoption with an `unknown` original.
- Before setup or adoption may publish `active`, prove the three exact producer package versions and the efibootmgr floor, the pinned unconfiguration tool inodes, and all five hooks by canonical content and executing installed command target. pacman gives configured HookDir entries precedence over the system hook directory for same-named hooks, so a same-named file in any configured HookDir, or an unreadable HookDir list, fails activation. A checkout, a stale package set, a stale source install, or an incomplete deployment fails before transition publication.
- Hook suppression under a top-level OmaSecBoot mutation is valid only for an owned transition whose token, boot ID, owner PID and process start time, ancestry, and root-owned manifest agree. An environment boolean is not ownership proof.
- `setup` and `sign` maintain signed EFI binaries plus enrolled `limine.conf` checksums with `ENABLE_VERIFICATION=no` and `ENABLE_ENROLL_LIMINE_CONFIG=yes`, written to `/etc/default/limine`, never to package-owned drop-ins. A managed setting found at its recorded original is repaired; any other value is refused as a conflict (`limine_managed_settings_are_repairable`).
- Do not reintroduce Limine `path: ...#hash` management while Omarchy boots UKIs through `protocol: efi`; warn on incompatible non-EFI paths instead of mutating them.
- limine-snapper-sync snapshot filenames can end in `.efi_sha256_<hash>`, `.efi_sha1_*`, `.efi_b3_*`, or `.efi_xxh_*`; that suffix belongs to the filename and is not a Limine path hash.
- Limine strips leading whitespace and generated sub-entries are indented; entry-boundary parsers match trimmed lines, not column-zero markers.
- The shared boot lock is taken by validating an inherited descriptor's ownership and the current pathname's device and inode, then calling `flock` on FD 200 before the critical section. A different pathname, an unchecked inherited descriptor, or validation without locking does not serialize boot mutations. Nested producer children inherit the repair lock on FD 201 without unlocking the parent's open file description; signal and exit rollback reacquire delegated locks before writing recovery state. After a reconstruction handoff, the inherited FD 200 is reacquired, or failing that the current pathname's lock; failing both leaves the transition for later reconciliation and the Limine post-hook returns fatal.
- Both Limine hook entry points admit an unrecognized caller that is a child of the owning transaction on its token, manifest, and ancestry proofs, because unconfiguration runs `limine-install`, which runs these hooks; a recognized producer is still resolved and locked first, a full restore is never admitted during a transition, and the pre-hook rejects every other hook-aware mutation during an OmaSecBoot transition. Every recognized producer acquires or recovers both locks and re-reads lifecycle state before an inactive no-op or an active lease; inactive non-restore producers reject the restore marker. The post-hook validates and locks inherited FD 200 or acquires the shared lock itself before repair. The transition guard also takes both locks and re-reads before an inactive no-op. Only the transition guard consumes `NeedsTargets`; an empty target stream blocks admission; the repair hook identifies the coordinator from the durable producer record, never from post-hook input.
- Both pacman guards block boot-mutating transactions during `transition` and `recovery-required`. While `active`, a transaction that changes `limine-mkinitcpio-hook`, `limine-snapper-sync`, or `sbctl` is refused, because a PreTransaction hook can prove only the installed version, not the incoming one. The removal guard preserves `omasecboot` and its runtime dependencies until the lifecycle is verified `disabled` or pristine; its target list equals the `PKGBUILD` dependency set and `tests/guards.sh` enforces that. The removal classifier runs under both locks; generic lifecycle mutation checks pacman's database lock after taking the locks and again immediately before publishing `transition`.
- Producer suppression and completion use the producer's immutable record, exact owner identity, boot ID, process start time, and current ancestry. Producer transactions bind that record, preserve producer outputs on failure, and select recovery only through the fixed package, Limine, snapshot, and restore registry; completion proves the artifacts discovered afterwards, so no pre-mutation inventory is recorded. `producer_reconstruction_preflight` is the only relaxed preflight and tolerates missing producer outputs only before fixed-registry reconstruction.
- Producer completion requires final-proof schema 2: every discovered non-Microsoft EFI artifact locally signed and sbctl-tracked, persisted after revalidating each proved hash and identity. Recovery of an interrupted package or UKI-build producer reruns `limine-mkinitcpio`, and recovery of a snapshot or restore producer reruns `limine-snapper-sync --no-force-save`, before repair; a normal completion trusts the producer's own output.
- Managed-settings ownership is written before tracking ownership; a tracking-only record is invalid. Recovery selects the newest complete pair in the validated incident chain and falls back to stable lifecycle ownership only when no incident transaction has complete authority.
- Incident seals are create-once (`mv --update=none-fail --no-copy`, coreutils 9.5 or newer) with the destination directory synced before the reference is published; a recovery chain admits at most 32 attempts.
- Recovery operations are exhaustive: producer roots admit only producer recovery, `enroll-secure-boot` roots without producer evidence only firmware recovery, `windows-bootnext` roots only Windows recovery, supported restore-policy software roots only software recovery, preserved `unconfigure` roots only unconfigure recovery. Firmware recovery derives its authority by traversing only hash-bound prior lifecycle records to the exact completed `activate-secure-boot-plan` transaction, stopping at a successful unconfiguration; it inherits the predecessor's backup, plan, rollback policy, and append-only firmware ledger, resolves only a terminal pending write through direct F0-F3 readback, repairs and proves EFI artifacts before continuing, and completes only after F3, a second EFI verification, and transaction-local firmware and artifact proofs. Technical readback uncertainty leaves pending evidence unresolved.
- OmaSecBoot does not stop or start `limine-snapper-sync.service`; the shared boot lock is the concurrency boundary. Full `limine-snapper-restore` runs without a parent shared lock: admit it only in stable state while the restore marker exists, serialize its post-repair, and reject it during `transition` and `recovery-required`. No producer lease, stale-transition reconciliation, or producer recovery runs while the marker exists, and OmaSecBoot never removes it; it lives under `/run/lock` and clears with the boot.
- `setup` provisions keys, the trust plan, and boot artifacts; `sign` is the lightweight repair path. Neither runs `limine-update` or rebuilds UKIs; the producers own boot-state regeneration. Both end with `sign_all_efi` so new snapshot UKIs are discovered and registered (`zz-sbctl.hook` re-signs only files sbctl already knows); config repair and checksum re-enrollment happen before that final signing.
- Current-config enrollment is unconditional: enroll and directly verify the current checksum in both `/EFI/limine/limine_x64.efi` and `/EFI/BOOT/BOOTX64.EFI` before final signing, never relying on change-since-start detection or upstream exit status. Build each target from the unsigned package executable in a same-directory staging file: enroll, locally sign, directly verify, sync, then replace atomically; never durably publish an unsigned boot target. Reject higher-priority Limine config candidates on the ESP before proving `/boot/limine.conf`.
- An enrollment or Secure Boot enablement instruction requires a read-only proof after final signing that every discovered non-Microsoft EFI artifact carries the local signature and sbctl tracking state.
- `sbctl list-files` is the tracked-file source of truth. Resolve `files_db` from one explicit plain top-level scalar in `/etc/sbctl/sbctl.conf`; without that file, match sbctl 0.18's legacy `/usr/share/secureboot/files.db` selection or the `/var/lib/sbctl/files.json` default; unsupported syntax fails closed. Direct database reads are fallback and cleanup paths. Each reader accepts exactly its source's shape, the CLI's array of entries or the database's object keyed by source path whose `file` equals the key, and synthesizes no field on a proof path; any other shape fails closed, and an unsupported CLI answer is never rescued by the database fallback. Keep `save_sbctl_file_entry` while Arch ships the affected sbctl release (trigger in the ledger).
- Pacman PostTransaction ordering stays `zz-sbctl` before `zzz-omasecboot`; package repair and the Limine post-hook cover different mutation sources.
- Windows uses `protocol: efi_boot_entry` so the managed path requests a direct firmware handoff instead of chainloading through Limine. BootNext is a one-boot request; never claim a successful Windows boot, PCR7 binding, stable measurements, or the absence of BitLocker recovery.
- Windows targeting parses `BootOrder` and the exact `File(\EFI\Microsoft\Boot\bootmgfw.efi)` node (case-folded, as Limine compares), maps the GPT HD node to one FAT ESP mounted whole with nothing mounted below it, validates the loader read-only, requires one active target and a case-insensitively unique Limine label, and proves numeric and Limine resolution agree. Reject ambiguity; never create or relabel firmware entries.
- The BootNext transaction reads the raw six-byte efivarfs value, publishes immutable current-boot, prior-value, exact-target, and open-`efibootmgr` executable evidence before mutation, repeats every proof immediately before its only `-n` call, and requires exact direct readback; it executes the validated open inode, never a reopened pathname. Any uncertain post-publication outcome stays `recovery-required`.
- Windows recovery admits only a validated `windows-bootnext` root and records its root write frontier, fresh boot ID, direct observation, planned action, and planned outcome before any repair. A root with no BootNext record resolves as `not-published`; a record whose write phase was not reached resolves only when the prior value remains exact; an observed prior as `prior-unchanged`; an observed target by restoring the exact prior; later-boot absence after a possible write as `consumed-unknown`, never as proof Windows booted. Present values are restored through the root-bound open inode; absence is restored by removing the variable file after re-proving its pathname, device, inode, and hash, because efibootmgr 18's `-N` mistakenly requires `Boot0001`; direct absence readback is required. Unreadable or unrelated state stays `recovery-required`.
- `windows setup` records the target, writes the managed block, enrolls, and signs in one invocation. `status` identifies Quattro's native `protocol: efi` chainload entries and never removes them. The menu fragment's guard is unprivileged and silent (`windows available`: the opt-in record exists and still matches one valid firmware target); its action runs privileged `omasecboot windows bootnext` before user-context `omarchy system reboot`, reboots only on exit status 0, and is never executed by automated verification. `windows bootnext` exits 3 when it completed lifecycle recovery and made no request.
- Windows disk-check prompts are not BitLocker recovery. OmaSecBoot never mounts or modifies NTFS and never infers hibernation from a failed mount. Windows Home follows Microsoft's documented Device Encryption decryption workflow; Pro, Enterprise, and Education may use documented BitLocker suspension; managed devices require administrator approval.
- The preflight evaluates firmware options, BitLocker signatures, and Microsoft loaders on internal GPT ESPs independently as `present`, `absent`, or `unknown`. A complete negative is a bounded observation, not firmware clearance. Every positive or unknown run requires an encryption-state check and recovery-key acknowledgment; any technical unknown prints guidance, returns nonzero, and has no override a firmware-mutating command may consume. External ESPs are not mounted or parsed; internal boot managers are located under both locks through the same read-only mount and loader proof the handoff uses; no signer metadata is inspected.
- Before any Setup Mode instruction, back up raw PK, KEK, db, and dbx data, attributes, hashes, absence records, the SetupMode, AuditMode, DeployedMode, and SecureBoot values, and the DMI identity fields (product UUID plus vendor, product, board, and BIOS identifiers, including the board serial). The conforming single OEM PK may be replaced only as an explicitly confirmed exception. Every current supported KEK and db entry must remain in the exact planned `-m -f` set. A firmware that already holds the whole plan is observed as enrolled and receives no firmware write; one that holds part of it has no F0 frontier and is refused when the plan is built and again before any firmware instruction; a database that cannot be read is reported as unreadable, never as a match. Unknown or unsupported trust entries block before any firmware instruction. Never preserve by subject name or repair with `--append`.
- There is no dbx writer. Only a confirmed PK-only firmware operation with present zero AuditMode and DeployedMode values is supported; missing mode variables, clear-all-only firmware, or changed KEK, db, or dbx state blocks before enrollment. Root db, KEK, and PK writes are guarded by the firmware-enrollment predicate at entry, before artifact mutation, and before every firmware write; the firmware-recovery predicate authorizes only validated continuation attempts.
- Each enrollment transaction binds the firmware-backup and trust-plan hashes before artifact mutation, records every firmware-write attempt before invoking the pinned sbctl executable, and records the command result plus direct readback. Before the first possible firmware write, restoration of pre-repair boot artifacts is durably disabled; the proved boot-artifact set is preserved across later failures. Firmware recovery may keep `restore` only while the cumulative ledger is empty and direct observation remains F0.
- Unconfiguration and its recovery derive immutable settings, tracking, Windows, stock-source, and package-tool evidence from the root intent; revalidate each Limine tool's package version, path, device and inode, and hash immediately before executing its open inode, while a completed intent's recorded tool version is historical evidence checked for shape only, so a later package pin does not invalidate a proved `disabled` state; run `limine-install --no-efi-register --fallback`, a final checked enrollment reset after both children, and an ESP-wide durability barrier; and publish `disabled` only after a final direct proof. Every phase is idempotent.
- Software `unconfigure`, PK reset, raw-key recovery, and firmware factory restoration are distinct. Package removal is permitted only from pristine state or proved `disabled` state: the last transaction is a completed unconfiguration, or a lineage of setup preparations and software recoveries back to `disabled` leads through hash-bound prior lifecycle records to one or to a pristine start. Removal preserves lifecycle records, transactions, firmware backups, the Windows opt-in record, local sbctl keys, and the lock pathname, and removes only `omasecboot`.
- The package owns `/usr/bin/omasecboot`, `/usr/lib/omasecboot/`, the three pacman hooks, the two Limine hooks, the tmpfiles declaration, license, README, `AGENTS.md`, and the `docs/` pages the README links to, all under one documentation directory so the links resolve there; `/var/lib/omasecboot` is declared through tmpfiles and is never package content; there is no install scriptlet. Neither guard triggers on install or upgrade of `omasecboot` itself, so the package can be upgraded in any state; upgrading during `recovery-required` is the intended way to receive a recovery fix. `PKGBUILD` dependencies stay resolver floors until the active-lifecycle update path in the ledger is resolved.
- CI proves package install, hook execution, guarded removal, blocked producer transactions, upgrade, and preservation in a disposable container with the two Omarchy producer packages assumed installed; it does not exercise lifecycle activation.

## Post-Change Verification

- Run `make test` after code, hook, install, packaging, or menu changes. `tests/package.sh` needs a git checkout plus makepkg, fakeroot, pacman, bsdtar, vercmp, jq, git, and make. `tests/package-root.sh` runs only as root in a disposable container with `OMASECBOOT_DISPOSABLE_ROOT=1`; CI runs it on every push, and `docs/release-checklist.md` carries the local Docker rehearsal to run before changing either package test or the workflow.
- Run `make lint` after any change: one `bash -n` per script, `shellcheck -x` over all of them, and the menu fragment parsed with `jq`.

## Conventions

- Bash with `set -euo pipefail`; ShellCheck clean.
- No `--` prefix on subcommands (`setup`, not `--setup`).
- Output helpers: `pass`, `fail`, `warn`, `act`, `die`; libraries return status and let the dispatcher decide.
- Quiet mode via `QUIET=true` (set by `--quiet`).
- Boolean checks on JSON documents go through `json_is`; a jq failure is a negative answer.
