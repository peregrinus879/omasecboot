# Changelog

What changed for someone who runs the tool. Git history holds the rest.

## Unreleased

- A Limine executable that is not sealed is never signed, wherever it stands, such as the copy Omarchy 3 left in `EFI/arch-limine`: signed, it would start under Secure Boot and read any `limine.conf` without checking it. `status` names one left unsigned, and blocks on one that carries your signature, as 0.1.0 could leave it. A second system's Limine that is not sealed, which 0.1.0 signed, is no longer signed: seal it over its own `limine.conf` with that system's tools to keep it starting with Secure Boot on. A sealed Limine of another system is signed as before.
- A file that carries Limine's marker but whose checksum slot does not tell whether it checks `limine.conf`, or that cannot be read to tell, is not signed, and the pass says so and fails.
- `setup` and `status` count sbctl rows for any Limine executable as harmful, the primary loader's included, and `setup` reads sbctl's list again after removing them.
- The seal is read in the slot layouts Limine's development branch adds; a seal that cannot be told is never taken as proved or as missing.
- The pass writes the Windows entry into `limine.conf` only together with a loader sealed over the new file, built and proved first: lost keys or a signing failure no longer leave the loader sealed over an older `limine.conf`, which stopped the machine with Secure Boot on or off. A hangup, an interrupt, a quit or the stop signal (TERM) cannot split the two renames, and a write the ESP did not confirm is said, with Secure Boot on or off, until a pass has synced the ESP.
- The watchers' pass keeps what a full pass found in `needs-attention` instead of replacing it and later clearing it.
- `setup` refuses, and the pass seals and signs nothing, on an ESP that users other than root can write, judged by the `uid`, `fmask` and `dmask` of the ESP's mount and by an idmapped mount of its device; `status` blocks on it and says what that costs. Omarchy's own mounts are writable by root alone.
- After `remove`, `status` warns while the loader carries your signature and no seal and the firmware still trusts your key, and blocks on it with Secure Boot on; `remove` says so as it finishes, unless the restored settings seal the loader.
- `status` warns against a restart only where a problem stops a start now, with Secure Boot on or with it on or off, as the problem decides; a Windows entry whose target is lost or unclear, a watcher that is not active and other problems a later update would meet no longer tell you not to reboot. `status` now blocks on a `limine.conf` that cannot be read or holds no menu entry besides OmaSecBoot's own, which it passed before although Limine would not start Omarchy, and warns for Secure Boot off as well where the firmware has no entry for the Limine loader and no raw fallback stands in. A problem that neither `sign` nor `setup` repairs ends the report with "resolve what is marked above, then run `sudo omasecboot status` again" instead of sending you to `setup`.
- `setup` tells boot entries it cannot read apart from a missing entry for the Limine loader, and no longer sends you to `limine-install` for them. A boot entry whose name is not valid UTF-16 no longer stops the reading of every other entry.
- For OmaSecBoot's Windows comment where it did not write it, the advice is now to remove the whole entry when it is OmaSecBoot's Windows entry edited by hand, which the next pass writes again while the Windows entry is enabled, and the comment line alone anywhere else: removing only the comment left two Windows entries. The advice to rename a Windows Boot Manager entry with `efibootmgr`, which cannot rename one, is gone.
- `version` and `help` refuse an argument they do not take, and `status --quiet` stays silent when it is not run as root.
- Every instruction to turn Secure Boot off, in `setup`, in `status`, before the package is removed and in the bug form, now reminds you of Windows' recovery key where Windows may be encrypted, as `remove` did. The way to avoid BitLocker's prompt ends with the protectors enabled again whichever way Secure Boot changed, and names the file, printout or USB drive the key was saved to beside the online places. `windows setup` says that the entry stays enabled when its pass fails.
- `setup` and `status` name a firmware that dropped its `SetupMode` variable after erasing every key, with the way back, instead of blaming efivarfs. The instruction to delete the Platform Key says to run `setup` again right before it after starting Windows or updating the firmware, since either can change dbx, which `setup` then refuses.
- A certificate held or written back under another owner no longer counts as lost, before an append as well as in the rebuild's list: the trust of EDK2-based firmware never reads the owner. A machine refused for that alone is now enrolled by appending. The rebuild says what a lost entry can cost, a device whose option ROM it verified; names an empty revocation list (dbx) on its own; no longer promises that a firmware update or fwupd restores dbx; and with only a backup taken in Setup Mode, offers restoring the factory keys instead of telling you to do so before it asks. The refusal names which of KEK and db kept its own entries, and a refused append plan names sbctl's `db_additions` setting as one cause.
- `status` names two missing Microsoft 2023 certificates as "A or B".
- A write the ESP did not confirm is no longer lost when a stop signal arrives during the renames or the loader's rename fails after it: it is said and recorded in `needs-attention`.
- `status` blocks, and the full pass fails, when a file that Omarchy's OS entries name is missing from the ESP, such as a kernel image deleted by hand; both passed before. They name `sudo limine-update`, which builds it again.
- An upgrade of the package on a machine that is set up, whose ESP users other than root can write or whose mount cannot be read, prints a warning.
- The package's removal warning says what removing it takes away: what re-seals the loader after an edit of `limine.conf` and repairs it after a Limine upgrade. An acceptance record says in its header whether it counts as evidence, and why not when its checkout is modified or an installed file differs from it, judged again after a command that installs or removes the package.

## 0.1.0 (2026-09-23)

The first release.

- `setup` is the one command: run it again after each step it asks for. It creates signing keys through sbctl, writes two Limine settings and remembers what stood there, seals and signs the loader, signs what arrived unsigned, enables two watchers and backs up the firmware's keys. In Setup Mode it adds the user's certificates beside the KEK and db entries the firmware holds and replaces only the Platform Key; where the firmware's key menu cleared KEK and db as well, it offers to rebuild them and lists what cannot come back. With Secure Boot on it refuses to create keys or sign anything unless the firmware's db holds this machine's certificate, and on a firmware in Audit Mode it writes nothing and says so. It warns before the Platform Key is deleted when KEK lacks Microsoft's 2023 certificate, offers a fallback loader where a machine has none, only into an empty place, and tells the user to turn Secure Boot on only when the firmware has an active boot entry for the Limine loader. Beside Windows it asks for the recovery key before the Platform Key is deleted and before it writes keys, reminds of it before Secure Boot is turned on, and says how to avoid BitLocker's prompt.
- `sign` is the converge-and-verify pass that the Limine hook and the watchers run. A file that `limine.conf` names with a path hash is never signed, under any spelling of its path or resource; a hash under a resource other than `boot():/` is noted, not failed, because only the firmware resolves that volume.
- `status` reports the firmware, the settings, the loader proof, the fallback, every signable file, an ESP that is running out of room, Microsoft's 2023 certificates that are missing, a machine whose firmware has no active boot entry for the Limine loader, the Windows entry, the hook and the watchers, and names the command that repairs what it found.
- `remove` returns the settings and the boot files to stock. It stops at a nearly full ESP before it changes anything, says before its question when upstream's install will replace another system's fallback loader, says so when the watchers could not be disabled, keeps its record until every OS entry upstream writes carries its hash again where the restored settings ask for hashes, and on a machine that is not set up says that there is nothing to remove.
- `windows preflight` looks for Windows and BitLocker volumes; `windows setup` adds an entry to Limine's menu that restarts the machine into the firmware's Windows Boot Manager entry; `windows bootnext` asks the firmware to start that entry at the next boot, once, without the menu. The entry stays behind Omarchy's entries through `omarchy refresh limine`, so Omarchy's default keeps starting by itself. Where a chainload entry for Windows stands beside a BitLocker volume, `status`, `windows setup` and `windows status` say that the two ways of starting Windows do not mix. A Windows Boot Manager entry whose name has blanks at its ends or characters outside ASCII is refused, because Limine is not proved to match it.
- pacman warns when the package is removed from a machine that is still set up; it never blocks the removal.
- Snapshot images and the fallback loader are never signed or sealed, sbctl's file list is never added to, the hook never fails a Limine tool, and nothing blocks pacman.
- `tests/acceptance-record.sh` records a hardware run, and `tests/acceptance-share.sh` makes the copies that are fit for a public issue.
- Hardware record: ASUS Vivobook TP3402VA, AMI BIOS 307, Omarchy 4.0.4, stages 0 to 7 with commit `2a8d324`, Windows Home beside it with device encryption on. The tool changed after the run in the ways C10 of `docs/upstream-contracts.md` lists, each with hermetic proof and no hardware row; `docs/maintenance.md` lists the rows owed.
